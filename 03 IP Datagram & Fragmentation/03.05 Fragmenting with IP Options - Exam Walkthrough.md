### 3.5 Practical Walkthrough — Fragmenting with IP Options (Exam 19.11.2024)

Every datagram fragment normally carries a **20-byte base IP header**. When the sender adds
**IP options**, the header grows — and the exam tests whether you keep using the right header
size at each step. This note documents the official exercise **and both accepted calculation
approaches**, because the grading sheet used the simplified one.

#### Reference Problem (CA1, 19.11.2024, Exercise 3)

> A host sends an IP datagram of **3000 octets** including **20 octets of IP options**.
> The link MTU is **1012 octets**.
> 1. How many fragments are generated? Justify.
> 2. Give the fragment offset of each fragment. Justify.

#### Step 1 — The Header Grows with Options

$$H = \underbrace{20}_{\text{base header}} + \underbrace{20}_{\text{options}} = \mathbf{40 \text{ bytes}}$$

* The **IHL field** of the original datagram is $H / 4 = 40/4 = \mathbf{10}$ (recall the base
  value 5 for a 20-byte header; each 4 bytes of options adds 1).
* Original **payload** to fragment:
$$D_{\text{data}} = 3000 - 40 = \mathbf{2960 \text{ bytes}}$$

#### Step 2 — Fragment Capacity: Two Accepted Approaches

**Approach A — Strict (options copied into every fragment):**
$$\text{Capacity}_A = \text{MTU} - 40 = 1012 - 40 = 972 \text{ bytes}$$
$$972 / 8 = 121.5 \implies \text{round down: } 121 \times 8 = \mathbf{968 \text{ bytes per fragment}}$$

**Approach B — Official correction sheet (fragments keep only the 20-byte base header):**
$$\text{Capacity}_B = \text{MTU} - 20 = 1012 - 20 = 992 \text{ bytes}$$
$$992 / 8 = 124 \implies \textbf{992 bytes per fragment (already 8-aligned)}$$

> **Exam strategy:** The professor's correction for this paper used **Approach B** (992).
> Always reproduce the course's official method first; mention the strict interpretation only
> if the question explicitly says options are copied into every fragment. Both must be in your
> notes — quoting the wrong one on the day costs the exercise.

#### Step 3 — Number of Fragments (Approach B, official)

$$N_{\text{frag}} = \left\lceil \frac{2960}{992} \right\rceil = \lceil 2.98 \rceil = \mathbf{3 \text{ fragments}}$$

#### Step 4 — Fragment Table (official answer)

| Fragment | Payload ($P_i$) | MF Flag | Offset (bytes before) | **Fragment Offset value** | Total Length |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **F1** | 992 B | 1 | 0 | $0 / 8 = \mathbf{0}$ | 1012 B |
| **F2** | 992 B | 1 | 992 | $992 / 8 = \mathbf{124}$ | 1012 B |
| **F3** | $2960 - 1984 = 976$ B | 0 | 1984 | $1984 / 8 = \mathbf{248}$ | 996 B |

* All three fragments share the same **Identification** value so the receiver can reassemble.
* Offsets `0 → 124 → 248` increase by exactly **124** per full fragment ($992/8 = 124$) —
  a quick self-check on the wire.

| F1 | 968 B | 1 | 0 |

$$\left\lceil \frac{2960}{968} \right\rceil = \lceil 3.06 \rceil = 4? \;\text{— No: } 968 \times 3 = 2904 < 2960 \text{ requires a 4th fragment of } 56 \text{ B}$$

| Fragment | Payload | MF | Offset |
| :---: | :---: | :---: | :---: |

| F2 | 968 B | 1 | 121 |
| F3 | 968 B | 1 | 242 |
| F4 | 56 B | 0 | 363 |

*This is why the professor's simplified method matters: it changes the fragment count
(3 vs 4). Follow the official correction (Approach B) for this exam's style.*

#### Rules Recap

1. Options inflate the **original datagram's** header (IHL grows in units of 4 bytes).
2. Fragment capacity per link = $\lfloor (\text{MTU} - H_{\text{fragment}}) / 8 \rfloor \times 8$ —
   payload of every non-final fragment must stay a **multiple of 8**.
3. Offset value = (bytes of original payload carried by earlier fragments) $/ 8$.
4. MF = 1 on all fragments except the last; the last fragment's payload needs no 8-byte alignment.

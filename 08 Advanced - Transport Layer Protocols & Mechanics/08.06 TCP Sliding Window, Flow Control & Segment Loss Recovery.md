### 8.6 TCP Sliding Window, Flow Control & Segment Loss Recovery

The flow-diagram exercise (25–35% of recent final exams) combines three mechanisms: the
**sliding window**, **cumulative acknowledgments**, and **loss recovery via duplicate ACKs**.
This note states the rules and shows how every message of a graded trace is generated.

#### The Sliding Window

* The receiver advertises its free buffer capacity in the **Window (Win)** field of every
  segment it sends (e.g. `Win=2000`).
* The sender may transmit only **up to Win bytes beyond the last acknowledged byte** — the
  "window" of unacknowledged data in flight slides forward as ACKs arrive.
* If the receiver shrinks the window, the sender throttles (**flow control**); when the
  advertisement is 0, the sender stops entirely until a window update.
* On exams the window is often expressed in **segments** ("sliding window = 2 segments"):
  sender may keep at most 2 unacknowledged segments in flight, then must pause for an ACK.

#### Acknowledgment Rules (cumulative ACK)

1. `Nack = N` confirms **all bytes up to N−1** and requests byte N next.
2. On receiving a data segment, the receiver returns `Nack = Nseq + Len` (the next byte it
   wants).
3. If a **gap** is detected (a segment arrives whose Nseq > expected), the receiver
   **repeats the last in-order Nack** — a **duplicate ACK**. It carries no new information
   except *"segment starting at byte N is still missing."*
4. The sender that receives a duplicate ACK **retransmits only the missing segment**
   (fast-retransmit behavior in the graded traces — not the whole window).
5. After the retransmission fills the hole, the receiver's cumulative ACK **jumps forward**
   over all buffered out-of-order data at once.

#### Invariant to Check Your Diagram

$$\text{Every data segment: } \text{Nseq}_{\text{next}} = \text{Nseq} + \text{Len}$$
$$\text{Every ACK: } \text{Nack} = (\text{highest in-order byte received}) + 1$$

Win values on ACKs come from the receiver's remaining buffer; Nseq on pure ACKs never moves.

#### Worked Trace (Final 16.01.2024, Exercise 2 — annotated)

*Setup:* A sends 2500 B (segments 1000 + 1000 + 500), B replies with 3000 B (3 × 1000) but its
**1st and 3rd segments are lost**; MSS = 1000 B; Win A = 3000, Win B = 2000; ISN A = 150,
ISN B = 100.

```text
Handshake:  A --SYN, Nseq=150, Win=3000------------------> B
            A <--SYN+ACK, Nseq=100, Nack=151, Win=2000--- B
            A --ACK, Nseq=151, Nack=101-----------------> B

A's upload (2500 B):
            A --ACK, Nseq=151,  Nack=101, Len=1000-------> B
            A --ACK, Nseq=1151, Nack=101, Len=1000-------> B
            A --ACK+FIN, Nseq=2151, Nack=101, Len=500----> B   (data + FIN)
            A <--ACK, Nseq=101, Nack=2652, Win=2000------  B   (2500 data + 1 FIN byte = 2651 bytes acked)

B's download (3000 B, segments 1 and 3 LOST):
            A <X-Seg1: Nseq=101, Nack=2652, Len=1000      B   [LOST]
            A <--Seg2: Nseq=1101, Nack=2652, Len=1000----- B   (gap: bytes 101..1100 missing)
            A <X-Seg3: Nseq=2101, ACK+FIN, Len=1000       B   [LOST]

Recovery:
            A --duplicate ACK, Nseq=2652, Nack=101-------> B   (B re-asks byte 101)
            A <--Seg1 retransmit: Nseq=101, Len=1000------ B
            A --ACK, Nseq=2652, Nack=2101----------------> B   (cumulative jump over buffered Seg2)
            A <--Seg3 retransmit: Nseq=2101, ACK+FIN, Len=1000  B
            A --ACK, Nseq=2652, Nack=3102----------------> B   (3000 data + 1 FIN byte)
```

**How each recovery number appears:**
* Seg2 arrives: expected byte is 101, but 1101 > 101 $\implies$ dup ACK `Nack=101`.
* Retransmitted Seg1 fills the hole; Seg2 was buffered $\implies$ ACK jumps to
  `Nack = 101 + 1000 + 1000 = 2101` (cumulative).
* Seg3 carries the FIN $\implies$ final ACK `Nack = 2101 + 1000 + 1 = 3102` (data + FIN's
  sequence number).

#### Same Rules, Window-Constrained (Final 2020)

The 2020 trace runs with **window = 2 segments** and **1404-byte segments**: A may send at most
two MA segments, then must wait for B's ACK before continuing. When MA4 is lost and MA5
(out-of-order) arrives, B answers the duplicate ACK `Nack=4213` (start of the missing
segment) and drops its window to `Win=1500` (half-freed buffer). A retransmits only MA4; B's
ACK then jumps to `Nack=7021` (4213 + 1404 + 1404 — covering retransmitted MA4 + buffered
MA5). Full trace in [[09.13 Final 2020 - TCP Transport and DMZ Routing]].

#### Exam Checklist for Drawing the Diagram

1. Establish: SYN / SYN+ACK / ACK with both ISNs and windows.
2. Data: Nseq chain with `+Len` steps; piggyback FIN on the last segment if the sender closes.
3. Loss: mark the lost segments; receiver keeps ACKing the **last in-order byte** (dup ACK).
4. Retransmit **only** the missing segment when its duplicate ACK is seen.
5. After the hole is filled: cumulative ACK jumps over buffered data (+1 if a FIN was in the
   buffered/retransmitted segment).
6. Close: FIN arithmetic per [[08.05 TCP Three-Way Handshake & Connection Teardown Math]].

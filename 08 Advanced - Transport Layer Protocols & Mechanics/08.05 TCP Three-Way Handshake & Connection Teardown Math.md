### 8.5 TCP Three-Way Handshake & Connection Teardown Math

Connection establishment and release are pure **sequence-number bookkeeping**. The two rules
below decide every value on the diagram:

1. **SYN and FIN each consume exactly 1 sequence number**, although they carry no payload.
2. **A pure ACK consumes 0 sequence numbers.** Only payload data (plus SYN/FIN) advances the
   byte stream.

#### Connection Establishment — The Three-Way Handshake

1. **SYN** — client requests the connection:
$$\text{SYN}=1,\ \text{ACK}=0 \quad | \quad \text{Nseq} = \text{ISN}_{\text{client}} \quad | \quad \text{Nack} = 0$$
2. **SYN + ACK** — server acknowledges and syncs back:
$$\text{SYN}=1,\ \text{ACK}=1 \quad | \quad \text{Nseq} = \text{ISN}_{\text{server}} \quad | \quad \text{Nack} = \text{ISN}_{\text{client}} + 1$$
3. **ACK** — client completes the handshake:
$$\text{SYN}=0,\ \text{ACK}=1 \quad | \quad \text{Nseq} = \text{ISN}_{\text{client}} + 1 \quad | \quad \text{Nack} = \text{ISN}_{\text{server}} + 1$$

*Why the "+1"s?* Each SYN consumes one sequence number, so the peer must acknowledge it: the
first data byte of the client will be $\text{ISN}_{\text{client}} + 1$.

#### Sequence Arithmetic During Data Transfer

$$\text{Next Nseq} = \text{Current Nseq} + \text{Payload Length (bytes)} \qquad \text{(add 1 more if SYN or FIN is set)}$$

* **Pure ACKs** (no payload): Nseq unchanged, Nack unchanged.
* **ACK numbers are cumulative**: Nack $= N$ means *"every byte up to $N-1$ is received; send
  byte $N$ next."*

#### Connection Teardown — The Math

A graceful close is a **four-segment exchange** (each side closes its own direction):

```text
Host A (active closer)                                     Host B
  |--- FIN=1, Nseq = X            (consumes 1 seq no.) ----->|
  |<-- ACK=1, Nack = X + 1        (pure ACK, consumes 0) ----|
  |        ... Host B finishes sending its own data ...
  |<-- FIN=1, ACK=1, Nseq = Y     (consumes 1 seq no.) ------|
  |--- ACK=1, Nack = Y + 1        (pure ACK, consumes 0) ---->|
```

* Each **FIN costs one sequence number**, exactly like a SYN; the peer's ACK must therefore be
  `FIN's Nseq + 1`.
* A FIN may **piggyback on the final data segment** (flags `ACK+FIN`): that segment advances
  Nseq by `Len + 1` (payload + FIN), and the peer's final ACK acknowledges data and FIN in one
  cumulative number. This is precisely the pattern of the graded
  [[09.08 Final January 2024 - Network Design and TCP Flow Control|January 2024 trace]] (message 6
  `ACK+FIN, Len=500`, and the closing ACK `Nack = 2652` covering data + FIN).
* **RST** instead of FIN = abrupt abort (no graceful arithmetic, no waiting for the peer).

#### Worked Micro-Example (handshake + close only)

Client ISN = 150, server ISN = 100, client then sends 2500 bytes, server nothing:

| # | Flags | Nseq | Nack | Note |
| :---: | :--- | :---: | :---: | :--- |
| 1 | SYN | 150 | — | client ISN |
| 2 | SYN+ACK | 100 | 151 | acks SYN (150+1) |
| 3 | ACK | 151 | 101 | handshake done |
| 4 | ACK, Len=1000 | 151 | 101 | data |
| 5 | ACK, Len=1000 | 1151 | 101 | data |
| 6 | ACK+FIN, Len=500 | 2151 | 101 | final data + FIN: next seq would be 2652 |
| 7 | ACK | 101 | **2652** | server acks 2500 data bytes + 1 FIN byte |
| 8 | FIN+ACK | 101 | 2652 | server closes too |
| 9 | ACK | 2652 | 102 | client acks server FIN (101+1) |

Every number above is generated by the two arithmetic rules — no memorization required.
